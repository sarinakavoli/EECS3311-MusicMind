## Documented Stage 2 changes (Section 3 / 4 of report)

- **PostgreSQL → SQLite** — reason: zero server setup for a solo build; impact: minimal; concrete repositories are SQLite-backed, `MemoryManager` façade unchanged.
- **`Repository<T, ID>` → `Repository<T>`** (per-user `save(userId, entity)` / `findByUser` / `deleteForUser`) — reason: the domain value objects (`ListeningProfile`, `UserPreference`) are immutable and do not embed their owner, so the original `save(T)` / `findById(ID)` shape could not be implemented cleanly; impact: interface reshaped before any implementation existed; SQLite repos + `MemoryManager` use the new shape.
- **`MusicService` gains `getTopArtists(timeRange)`** — reason: F1 aggregates genres, which Spotify exposes only on artists, but `getTopItems` returns `Track`; impact: additive method implemented by `SpotifyAdapter` and passed through `RetryingMusicService`.
- **LLM provider = OpenAI** (`OpenAiProvider` via the `LLMProvider` seam, per Stage 1) — impact: real provider used when `LLM_API_KEY` is set; otherwise no provider and features with a Stage 1 fallback use a labelled computed one. `MockLLMProvider` is test-only (R17).
- **Auth is PKCE (public client)** — reason: no server to hold a client secret; impact: only `SPOTIFY_CLIENT_ID` is needed; `.env.example` dropped the secret/Postgres vars and added `DATABASE_PATH`.
- **Gradle 8.14.3 → 9.1.0 + foojay toolchain resolver** — reason: Gradle 8.14.3 cannot run on JDK 25, and a machine with only JDK 25 has no Java 17 toolchain; impact: `./gradlew` works on JDK 25 with no `JAVA_HOME` setup, the project still compiles as Java 17, and the first build downloads a JDK 17 if none is found (needs network).
- **JavaFX 17.0.6 → 21.0.13** — reason: on macOS 26 the 17.0.6 native window code crashed the app on launch (`NSTrackingRectTag` exception in `libglass`); impact: GUI launches; 21 is an LTS line that still supports Java 17, and no GUI code changed.
- **Artist genres come from MusicBrainz, not Spotify (R18)** — Original: Stage 1 reads genres from Spotify artist metadata. Change: `GenreEnrichingMusicService` (Decorator over `MusicService`) fills `Artist.genres` through `GenreService`/`MusicBrainzAdapter` (Adapter), cached by artist id in `artist_genre`. Reason: live testing showed Spotify returns no `genres` to a Development Mode app. Impact: F1, F2, F4, F5 get a genre signal again; coverage can be partial, which `ProfileBuilder` reports, and the CLI credits MusicBrainz. Genres are derived data, so caching them respects the Spotify terms.
- **Search sends genre as a plain keyword (R19)** — Original: Stage 1 F3/F4 pass genre to Spotify search as a `genre:` filter. Change: `SearchQuery.toSpotifyQuery()` appends the genre as a keyword (skipped if the keywords already contain it); `year` and `artist` filters stay, and LLM filters outside `search.allowedFilters` are dropped. An empty F3 result is retried once with the keywords alone before the no-results notice. Reason: live testing showed `upbeat indie running genre:indie` returned 1 track, `upbeat indie running` returned 20. Impact: F3 and F4 (`CandidateRetriever.byGenre`) return results; genre still ranks results.

## Design patterns (must be evident in code)

Adapter (`MusicService`/`SpotifyAdapter`), Strategy (`RecommendationStrategy` + Abstract + 3 concretes), Command (`PlaylistCommand` + concretes, `PlaylistManager`), State (`SessionState` + phases, `AgentSession`), Facade (`MusicAgentFacade`). Plus Repository (persistence) and Decorator (`RetryingMusicService`, `GenreEnrichingMusicService`).
- **Discovery excludes known tracks; artist-album page size (Task 20)** — Original: `discover` could return tracks from the user's library as "familiar" picks, and one `spotify.albumPageSize=50` served both album endpoints. Change: `RecommendationEngine.recommend(profile, spec, feedback, allowLibraryTracks)` (the Stage 1 3-arg form delegates with true; `MusicAgentFacade.discover` passes false per call, nothing is remembered; known track ids from the profile are excluded too) removes top, saved and recently played tracks from every pool, so the familiar pool becomes new tracks by artists the user knows; F5 can allow library tracks again. `spotify.artistAlbumPageSize=10` and `spotify.albumTrackPageSize=50` replace the shared key. Equal scores keep source order. Failed-read notices and the all-reads-failed error are short messages with a count, and the "library excluded" constraint is reported only when it applies. Reason: live test showed 13 of 20 results came from the user's history (Stage 1 F4 says exclude tracks the user already knows) and `/artists/{id}/albums` returns HTTP 400 above limit 10. Impact: F4 results are all new to the user; F5 and Task 10 are unaffected.
- **Saved tracks are read up to `spotify.maxSavedTracks` (Task 21)** — Original: `getSavedTracks` shared the 500-item paging limit (`spotify.maxItems`), so a larger library silently lost tracks and discover could suggest them as new. Change: saved tracks have their own cap (default 5000). When a read stops at the cap with more left, the returned list is a `TrackList` (an `ArrayList<Track>` with `isTruncated()`), which passes unchanged through `RetryingMusicService`, `GenreEnrichingMusicService` and `SpotifyTool`, so no `MusicService` signature changes; `MusicAgentFacade` adds the `text.savedTracksCapped` notice to `ListeningProfile.notices` and to the discover notices. Reason: a silent cut made F4's "exclude known tracks" wrong without telling the user. Impact: additive class and config key; the profile is marked partial when the cap was hit.
- **Same-name MusicBrainz artists give no genres (Task 21)** — Original: `MusicBrainzAdapter.findMatch` returned the first candidate whose name (or alias) matched and whose score reached `musicbrainz.minScore`. Change: if more than one different candidate passes both checks, the lookup returns no genres, as a cached no-match (nothing is logged to the user). Reason: two artists sharing a name (for example two bands called "Nirvana") made the first hit a guess, and wrong genres are worse than none. Impact: some artists show no genres; `GenreEnrichingMusicService` caches the empty result like any other no-match.
- **MusicBrainz outage pause (Task 21)** — Original: every artist was looked up even while MusicBrainz was failing, so one run could wait on dozens of timeouts. Change: after `musicbrainz.maxConsecutiveFailures` (3) failed lookups in a row (timeouts, connection failures, server errors; a rate-limit 503 never counts, and requests are spaced `musicbrainz.minIntervalMillis`=1100 apart), lookups are skipped for `musicbrainz.cooldownSeconds` (300); a skipped lookup is unknown, so it is not cached and counts as a failure in the existing partial-genres notice. Reason: a run must finish quickly during an outage. Impact: none when MusicBrainz works; one failed lookup after the pause ends starts the next pause.
- **Stored profile keeps artist genres and track artists; old profiles are rebuilt (Task 21)** — Original: `derived_json` kept artist and track ids only, so a stored profile scored differently from a fresh one. Change: it also keeps each top artist's genres (MusicBrainz data) and each top track's artist ids; profiles stored before this load without them, and `AppController.discover` rebuilds a stored profile older than `profile.maxAgeHours` (24). Reason: F4 scoring uses genre affinity and known artists. Impact: derived data only, no names or titles.
- **Review hardening (Task 21)** — Playlist adds and removals are split into `spotify.addBatchSize` batches and each batch is retried on its own (a retry never re-sends an earlier batch); `OAuthTokenStore.accessToken` opens the browser only after a 400 or 401 from the token endpoint; `.spotify-tokens.json` is created and rewritten as owner-only where POSIX permissions exist; the OAuth callback page HTML-escapes its text and ignores a callback with the wrong `state`; F1, F2 and F3 show short messages from `musicmind.properties` instead of raw errors (`ToolResult` gained an optional `cause`).
- **Command pattern, PlaylistManager and snapshot undo (Task 9; R10, R11, R12)** — Original: Stage 1 lists `PlaylistCommand` (`execute`, `undo`) with five concretes and `PlaylistManager` (`history`, `execute`, `executeAll`, `undo`). Change: the five commands work through `MusicService`; `CreatePlaylistCommand.undo` unfollows the playlist, and `RemoveTrackCommand`/`ReplaceTrackCommand` re-add and then reorder to the original index. `executeAll` undoes the commands already applied if one fails and rethrows, and records a successful batch as one undo step (`BatchCommand`). `PlaylistManager.modify(current, commands)` saves a snapshot first; if the database is down the change is refused with a clear message, and `undo` with an empty stack restores the latest snapshot (`MemoryManager.loadLatestSnapshot`), or says why it cannot. `ResponseParser.parseCommands(json, PlaylistContext)` binds `CommandSpec`s to real tracks (positions or ids from the playlist, tracks to add from Spotify search, never from the LLM). Reason: R10 needs undo across CLI runs and the snapshot must exist before a change is made. Impact: additive members `PlaylistCommand.playlistId()` and `describe()`, `PlaylistChangeException`, `PlaylistContext`, `PlaylistManager.modify/snapshotBeforeModify/restore(int)`, `PlaylistHistoryRepository.findLatestByPlaylist`, config keys `command.*` and `text.cmd*`; Tasks 10 and 11 call `modify`. A snapshot stores only ids and the playlist name.
