1 Project overview and implementation status

1.1 The application

MusicMind is an AI music-discovery and playlist-management agent built on the Spotify Web API. A listener types a goal in plain words, for example "a 90 minute study playlist, mostly familiar but with some new artists". MusicMind reads the listener's own Spotify listening data, turns the goal into a checked plan, retrieves candidate tracks, selects and orders them with its own deterministic recommender, validates the result against constraints (length, explicit content, blocked artists and tracks, duplicates), and creates or edits a real private playlist. It can also describe the listener's taste and how it changed, search in natural language, recommend new music, remember preferences and feedback, explain its choices, negotiate when a request cannot be met, and undo or restore earlier versions of a playlist.

Users. Individual Spotify listeners (Premium account required by Spotify for development apps) who want goal-driven playlists and controlled discovery, with a visible reason for every choice. Spotify development-mode apps allow at most five listed users without a quota extension.

1.3 How the AI and LLM take part

The LLM is a planner and narrator; deterministic code decides and acts. It is called through LLMProvider.complete (the interface has no parse(); ResponseParser reads the replies) by these five places. Stage 1 names the first and third only ("two components"); the others are added for language tasks, and none of them is sent a Spotify title, artist or album name (Section 4.1, "November 6"):

  • Planner: turns a goal, a search text or an edit instruction into a structured, validated plan (PlaylistSpec, AgentPlan, SearchQuery), and words the options offered when a request cannot be met (F11).
  • MusicAgentFacade (fromLlm): one summary sentence for the taste profile (F1) and a short narrative for taste change (F2), from genre weights and counts. ProfileBuilder and TrendComparator themselves make no LLM call.
  • ExplanationService: a grounded explanation of a playlist, which ResponseParser.verifyExplanation checks against the recorded decision trace.
  • PlaylistEditor: turns a free-text edit into commands (tracks to add always come from Spotify search, never from the model).
  • GoalFitReviewer: a removal-only review of already retrieved tracks (see 1.5 and Section 4).

The LLM never names or adds a track. Selection, ordering, length and validation are computed. Every model reply passes through ResponseParser, and a failed or rejected reply falls back to a computed result that is labelled as computed. With no LLM_API_KEY the features that need the model say so, and F1, F2 and F3 use labelled fallbacks.

The agent behaviour is multi-step planning and tool use: AgentSession.run() moves through the states Idle, Planning, Retrieving, Selecting, Validating, Executing and Done (Failed on any error); ToolManager runs the Spotify and memory tools; MemoryManager stores preferences, feedback, sessions, snapshots and candidates.

1.5 Limitations and incomplete work (stated plainly)

The detail and the evidence for each point are in docs/STAGE1_CONFORMANCE.md (section 7) and docs/DAILY_TEST_NOTES.md.

  • Goal fit is improved but not proven. In the author's first GUI test (November 2) the songs for a "workout" goal did not suit it. Fixes followed (activity searches, a removal-only goal review, scoring changes). On November 4 a further live run showed library songs chosen by taste alone still did not fit ("slow dance" got a pop song), so Create now keeps a familiar song only when it fits the goal by its artist's leading three genres or by its own Last.fm song tags, and adds songs that Last.fm lists under the goal's tags (Section 4.1). These rules are covered by tests. On November 6 the author ran Create for "slow dance" on her real accounts and Billie Jean no longer appeared; other goals were not re-run, so it is not known that playlists reliably fit their goal. LASTFM_API_KEY is optional but recommended; without it MusicMind shows no genres or tags and the tag features are off.
  • Not run against the real accounts: F11 with a real conflict (the prompt was only checked with stand-in text and in tests); delete (delete); recreating a deleted playlist from a snapshot; the GUI buttons Undo, Restore, like, not-for-me, Save and candidate controls pressed by a person (the same controller calls were run from the CLI for Undo and Restore); successful feedback and the other preference keys on the real account.
  • GUI redesign done; not yet re-tested by hand end to end or re-screenshotted. After the author's own user testing, the GUI was redesigned and merged on November 4 (dark theme, left-hand menu, plain wording and a description on every screen). It closes the gaps in docs/GUI_TEST_FINDINGS.md that this report listed before: a Delete button, pickers for blocking artists and songs, a candidate choice in the Create dialog, and artist names in track rows. It is covered by view-helper and controller tests, but the author's own pass over every screen is still to come, and the screenshots and demonstration videos will be made after it.
  • No automated tests drive the GUI views. There is no JavaFX or TestFX test of a view. What a view shows is built in ViewFormat and tested without JavaFX (ViewFormatTest, ControlLockTest), the logic behind each button is in AppController and has controller tests that the CLI tests share, and the screens were checked by hand (the author's tests and read-only live runs, docs/GUI_TEST_FINDINGS.md). A wrong layout or a button wired to the wrong call would be found only by hand.
  • Past week is thin by design. Spotify has no top items for a week, so Your Taste builds that range from the recent plays (Spotify keeps only the last 50) and labels it so. It is left out of Trends.
  • Last.fm needs a key and has limits. The key is optional but recommended; without it MusicMind shows no genres or tags and the tag features are off. A Create run reads at most 30 songs' tags and stops after about 15 seconds, so a slow Last.fm only lessens the tag signal; a song Last.fm does not know falls back to the genre rule. The Last.fm code is unit-tested against a local stand-in server. A read-only live check with a Last.fm key on Nov 4 (planning, retrieval and selection only, no playlist created) found no off-goal familiar songs for "slow dance" and no Nirvana for "music for studying" (mostly lo-fi and ambient, a few weak tag picks); "workout" still picked several songs by one hip-hop artist, because Last.fm has no tags for them and hip hop is a workout genre. The author's November 6 run of the Last.fm build (Section 6.2) covered Create "slow dance", Find Songs, Discover, Your Taste and Modify; Create for "workout" and "music for studying" was not re-run.
  • Search by description is weak. Spotify matches title words and this app has no tempo or mood data (Spotify provides no audio features to this app), so "mellow alternative for studying" returns poor results. Title and artist searches work.
  • Genre data is partial. It depends on Last.fm (MusicBrainz until November 5; the 13 of 20 figure below is from the first MusicBrainz run), and some artists have none. On November 6 the author ran the Last.fm-everywhere change on her real accounts and reported it worked. Trends and discovery say when coverage is partial.
  • Policy correction (November 3). The first version of the goal-fit review sent track titles and artist names to OpenAI. Spotify Developer Policy section III item 14 forbids ingesting Spotify Content into an AI model. It was changed the same day to send track ids and genres only (details in Section 4). The review is now less precise, does not judge tracks with no known genre, and was not re-run live.
  • Open policy question (F6 edit prompt). The prompt that turns an edit instruction into commands sends the model each track's id, explicit flag and length in minutes (no titles or names), because edits such as "15 minutes shorter" or "remove explicit" need them. Whether this counts as Spotify Content under the policy is unresolved and is for the author to decide.
  • Commit schedule. Period 1 (October 20-26) has no code commits and missed its minimum; the single 5-point deduction therefore applies (Section 6).
  • Remaining work at the time of writing: for Stage 2, demonstration videos (links are placeholders in Section 7), cost figures (Section 5), merging the stage2-alignment branch, retaking the GUI screenshots and a final hand test of the redesigned GUI. How it works. The goal and any flags (--minutes, --no-explicit, --familiar, --name, --no-candidates) become an AgentRequest. AgentSession.run() then walks the states: Planning (the LLM parses the goal; the mood becomes genres through MoodGenreMap); Retrieving (one Spotify read shared by all later steps, the goal-fit review, then the feasibility check, which starts F11 if the request is infeasible); Selecting (user candidates first, then BalancedStrategy, then a review of the final picks); Validating (a violation sends the run back to selection, at most 3 times); Executing (CreatePlaylistCommand then AddItemsCommand through the Command invoker); Done (store the session and write the explanation). The LLM's role: the goal-fit review and the November 3 policy correction

Original. Stage 1 gives the LLM no part in choosing tracks, and the implementation plan's constraint 2 says "the LLM never selects tracks and never receives bulk catalogue data".

Change. Since November 2 the LLM reviews real tracks that were already retrieved and may only return ids to remove (GoalFitReviewer, in RetrievingState and again on the final picks in SelectingState, bounded per run). It never names or adds a track, ids it was not given are ignored, and selection and order stay deterministic. The review is best effort: with no LLM, a failure, a malformed reply, or a reply that would remove too much, nothing is removed and a notice says it was skipped.

Reason. The author's live test produced unsuitable "workout" songs and Spotify gives no audio features.

Correction on November 3. The first version sent OpenAI each track's id, title and artist names. Spotify Developer Policy section III item 14 forbids ingesting Spotify Content into an AI model. This was found while writing the documentation and fixed the same day (commit 1b18d24), test first: the prompt now carries only the track id and the genres MusicMind already knows for it (from the search that found it, the listener's profile, or cached genres). A track with no known genre is not sent and is kept. A reflective test (PromptBuilderTest, hardened in commit 4211b8b) calls every PromptBuilder.build* method and fails if a prompt contains a track title or artist name.

Impact. The constraint now holds in this form: ids and genres, no Spotify titles or names. The review is less precise than a title-based one and cannot judge tracks without a genre. It is not proven to improve playlists on the real account, and it costs up to three extra LLM calls per create.

Open question. The F6 edit prompt sends each track's id, explicit flag and length in minutes (no titles or names). Whether that counts as Spotify Content is undecided and is for the author to decide.
